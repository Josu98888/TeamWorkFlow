- 2026-10-13 S7.5: the mechanism lives in `ConsumedEventProcessor.accept` (S7.1): a subject tenant that differs from the payload `tenantId` (missing, empty, not a uuid, null or different case) is discarded before the transaction, acked, and logged as `Discarding event with a tenant mismatch on <subject>` without payload. `src/events/tenant-mismatch.spec.ts` proves it for every consumed subject (billing handlers including purge, and `employee_created` through a stub handler until S8.1): the handler never runs and no database write or publish happens.
- 2026-10-13 S7.4: `TenantPurgeHandlers` (`src/tenants/tenant-purge.handlers.ts`). Only a `cancelled` tenant is purged; it is claimed with `updateMany(status: CANCELLED)` (count other than 1 throws `TenantStatusConflictError`, so a concurrent reactivation rolls back and the redelivery is ignored). Then refresh tokens, reset tokens, invitations, users and processed events of that tenant are deleted, leaving the `Tenant` tombstone (`id`, `name`, `DELETED`; plan, `features` (`Prisma.DbNull`), `planUpdatedAt` and the three status dates cleared). The `ProcessedEvent` row of the purge event is deleted too: status `DELETED` makes a redelivery a no-op (a late event may leave one id-only row, no personal data). Other statuses and unknown tenants are ignored; no event (AGENTS lists none); other tenants and `platform_admin` untouched. The spec shows the purged email can register again with the real `AuthService.register`. S8.1 must ignore `DELETED` tenants.
- 2026-10-13 S7.3: `TenantPlanHandlers` (`src/tenants/tenant-plan.handlers.ts`) stores `plan` (`fromWirePlan`), `features` and `planUpdatedAt` from `subscription_created` (instant = `occurredAt`) and `plan_changed` (instant = `effectiveAt`); no event. One `updateMany` requires `status != DELETED` and `planUpdatedAt` null or `<= at`, so stale events and deleted tenants match nothing with no read-then-write race; an equal instant is applied. It applies to a `cancelled` tenant because a resubscribe sends `plan_changed` before `subscription_reactivated`. An invalid payload (plan not `basic|pro`, `features` missing, an array or with non-boolean values, `plan_changed` without a valid `effectiveAt`) throws the new `PoisonEventError`; the processor rolls back, logs without payload and acks (other errors still nak). `verify` returns the stored values (real `AuthService`). No schema change.
- 2026-10-13 S7.2: `subscription_cancelled` and `subscription_reactivated` extend `billingTransition`. Cancel from `active`, `past_due` or `suspended` (no-op when `cancelled` or `deleted`): `cancelledAt` = event `occurredAt`, keeps `pastDueSince`/`suspendedAt`, revokes supervisor and employee refresh tokens, emits `tenant_cancelled`. Billing events while `cancelled` stay no-ops; the `ACTIVE` change of `payment_received` also writes `cancelledAt: null`. The spec uses the real `AuthService`: supervisor/employee get `tenant_cancelled` on verify and login and `invalid_token` on refresh; owner/admin pass verify with `tenantStatus: 'cancelled'`; reactivation restores access.

Per event: parse the envelope (uuid `eventId` and `tenantId`, ISO `occurredAt`), check the subject tenant against the payload (S7.5), then one transaction inserts `ProcessedEvent` with `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`, so a duplicate does not abort the transaction; count 0 = duplicate: no handler, ack) and runs the handler; effects (publishes) run after commit and a failure is logged without the error text. Malformed envelopes are logged without payload and acked; a throwing handler rolls back both writes and the message is naked. DEFAULT(auth): `payment_overdue` while `suspended` is a no-op (would restore access). Dates store the event's `occurredAt`. The write is `updateMany({ id, status: <read> })` and must count 1, else `TenantStatusConflictError` rolls back and JetStream redelivers. A billing `eventId` that is not a uuid is discarded as poison (`ProcessedEvent.event_id` is uuid): `billing` must emit uuid event ids. Real NATS flow covered by S10.3. No dependency, schema or env change.

- 2026-10-12 S3.4: login order is lookup by normalized email, then lock check, then Argon2 verify, then active/deleted-tenant guard, then failure count or success. Unknown email and locked accounts verify against a lazily computed dummy hash so they cost the same as a real attempt. Attempts during an active lock neither count nor extend it (the lock is exactly 15 minutes from the 5th failure). The 5th failure sets `lockedUntil` and resets the counter to 0 in a second update, so after expiry the count starts fresh with no special case; the increment itself is atomic (`{ increment: 1 }`). A successful login writes only if the counter or lock is non-zero. The login spec fakes `common/crypto/password` (cheap hash) to keep the parallel suite fast, and `password.spec.ts` got a 30 s timeout because real Argon2 (64 MiB per hash) timed out under parallel load.

The token pair is issued inside the transaction with the `tx` client; events are published after it resolves, in order `tenant_created` then `user_created`. `name` is not stored (no column); it only travels in `user_created`. DTO limits: `tenantName`/`name` 1-100 chars after trim, email max 254, password 8-128. The 422 for extra fields (`role`, `tenantId`) comes from the global pipe (`whitelist` + `forbidNonWhitelisted`), tested through `createValidationPipe()` against `RegisterDto`.
